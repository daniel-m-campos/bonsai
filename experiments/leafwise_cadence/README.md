# Leafwise cadence probe (stage 0)

`cadence.cu` prices the fixed per-round cost F of the device leafwise round designed in [docs/architecture/20-cuda-leafwise.md](../../docs/architecture/20-cuda-leafwise.md), before any engine code exists. It replays that round's launch, sync and staging skeleton 25,500 times (255 splits per tree x 100 trees, the issue #268 protocol) against a balanced 256-leaf schedule on 16M rows: one 20 B pinned upload, three partition-shaped launches, a device-to-device copy-back of the parent's range, a pinned 8 B download and sync, two histogram-shaped launches plus a subtraction, a find and a reduce, a pinned 112 B download and sync, and the host heap push and pop. The kernels are trivial by design, touching one element each, because stage 0 measures overhead rather than compute; the design's model is fit time is roughly the depthwise compute volume plus rounds times F. Four configurations run back to back so the total splits into buckets: `full`, `no_copyback` (F itself, since the device-to-device copy is leafwise-specific data movement and not fixed overhead), `no_syncs` (differences against `no_copyback` to isolate sync latency), and `floor` (every grid forced to one block, no copy-back: the pure launch and sync floor). Build and run with `nvcc -O2 -arch=sm_89 -o cadence cadence.cu && ./cadence <pod_id>`, which writes one JSON object to stdout. The 100 us budget and the 300 us kill line come from doc 20's admission section: at F = 100 us the round cadence costs 2.6 s over a 100-iteration fit, which lands under LightGBM's CUDA leafwise 24.4 s at 16M against bonsai's 17.2 s depthwise anchor, and above 300 us the thesis is wrong and the design returns to the batched-K question.
